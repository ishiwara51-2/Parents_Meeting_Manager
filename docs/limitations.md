# 既知の制限事項（プロトタイプ v0.1.0）

本ドキュメントは、保護者面談調整ツール（プロトタイプ）の既知の制限事項をまとめたものです。
各フェーズの引き継ぎメモ（`docs\handoff_phase*.md`）における「保留」「未解決」項目を集約しています。

---

## 1. シングルユーザー・シングルテナント前提

- 1 教師・1 インスタンスを前提とした設計です。マルチユーザー・マルチテナントには非対応です。
- 同一 `%APPDATA%` を複数ユーザーで共有する環境での動作は保証しません。
- `FileDraftRepository` のスレッドロック（`threading.Lock`）はクラスレベルのため、将来マルチテナント化する際は per-instance Lock への変更が必要です。（handoff_phase3_4）

---

## 2. SQLite ではなくファイルベースのローカル DB（JSON）

- プロジェクト・回答・ドラフト等のデータはすべて `%APPDATA%\meeting-scheduler\` 配下の JSON ファイルに保存されます。
- **同時アクセス制限**: 同一プロセス内のスレッド排他は `threading.Lock` で行っていますが、複数プロセスからの同時書き込みは非対応です（プロトタイプはシングルプロセスのため実害なし）。
- **ファイル蓄積**: 過去ドラフトはすべてファイルとして残置されます（requirements.md §4.9）。プロジェクト数・面談回数が増えると `drafts/` フォルダに大量のファイルが蓄積する可能性があります。定期的な手動クリーンアップが必要です。（handoff_phase3_4）

---

## 3. Google Forms API のレート制限・ポーリング間隔

- 回答の取り込みは**定期ポーリング方式**（既定: 60 秒間隔）です。リアルタイム受信（Pub/Sub プッシュ）には非対応です。（requirements.md §1.2）
- Google Forms API のクォータ超過時（HTTP 429）は最大 3 回の指数バックオフリトライ（1→2→4 秒）を行い、それでも失敗した場合は 503 エラーを返します。短時間に大量ポーリングを行う用途には向きません。（handoff_phase2_3）
- `forms.responses.list` API のレスポンス並び順（昇順/降順）は未確認ですが、本ツールは集合差分で未取得を検出するため順序非依存に動作します。（handoff_phase2_3）
- ポーリング中（最大数秒〜数十秒のブロッキング処理）は他の API リクエスト処理が遅延する場合があります（同期実装のため）。（handoff_phase2_3）

---

## 4. スケジューラの解最適性

- OR-Tools CP-SAT ソルバーを使用していますが、**ソフト制約の最適解は近似**です。CP-SAT の時間制限内（デフォルト設定）での最良解を返します。
- ハード制約（候補日時範囲、教師不可時間帯、1 コマ 1 生徒等）で解なしの場合、緩和を行わず「解なし」として未配置生徒リストを返します。（requirements.md §4.6.3）
- ソフト制約の重みバランスによっては直感に反する解が得られることがあります。日程案表示画面のドラッグ＆ドロップで手修正してください。

---

## 5. PDF の制限

- **フォントサイズの自動縮小**: 候補日数（列数）が増えると、セルのフォントサイズが 9pt → 最小 6pt まで自動縮小されます。日数が多い場合（9 日超）は複数ページに折り返されます。（docs\pdf_decisions.md、handoff_phase5_1）
- **PDF 保存場所**: `%APPDATA%\meeting-scheduler\projects\<project_id>\output\` への PDF 保存は Phase 5.2 時点では未実装です。ブラウザのダウンロードフォルダに保存されます。
- **プロジェクト status の `finalized` 遷移**: PDF ダウンロードを行っても、プロジェクトの status は `draft_saved` のままです（`finalized` への遷移は未実装）。（handoff_phase5_2）
- フォントファイル（`backend\app\fonts\NotoSansCJKjp-Regular.otf`）が欠損している場合は PDF 生成エラーになります。エラー内容は `app.log` を確認してください。（handoff_phase6_1）

---

## 6. OAuth・認証の制限

- OAuth リフレッシュトークンは `%APPDATA%\meeting-scheduler\config\oauth_token.json` に平文保存されます。ファイルへのアクセス権限は OS レベルのユーザー権限に依存します。
- `oauth_token.json` はリフレッシュトークンを含むため、**絶対にリポジトリへコミットしてはなりません**（`.gitignore` で除外済み）。
- GCP の OAuth 同意画面を「テスト」モードで運用しているため、外部ユーザーへの公開はできません。本ツールは実装者本人のみが使用してください。
- Google アカウントの認可を取り消した場合や `oauth_token.json` を削除した場合は、再度認証フローを実行してください。
- `finalized` ステータスのプロジェクトでも `POST /drafts/unlock` によるアンロックが可能です。運用上の問題はありませんが、将来的には `finalized` からの unlock を禁止することを検討してください。（handoff_phase3_4）

---

## 7. エラーリカバリの粒度

- バックエンドのエラーハンドリングは主要パスをカバーしていますが、細粒度のリカバリ（部分的な書き込み失敗時のロールバック等）は実装していません。
- フロントエンドでは `ErrorBoundary` により予期しない例外をキャッチしますが、「ページを再読み込みしてください」という案内のみで、詳細なエラー内容の表示は行いません。（handoff_phase6_1）
- ドラッグ＆ドロップで候補日時外のスロットに移動した場合は警告ダイアログが表示されますが、操作自体は許可されます（ハードブロックしません）。

---

## 8. フロントエンドの制限

- **DnD 後の再スケジューリング**: 「再編集」ボタンをクリックして `SchedulePage` に戻ると、スケジューリングが再実行されます。前回 DnD 編集した内容は引き継がれず、新たな最適解から編集を開始します。（handoff_phase4_4c）
- **保存完了画面のドラフト内容表示**: 保存完了画面にはドラフトの割り当て内容が表示されません（「日程案が保存されました。」の固定メッセージのみ）。（handoff_phase4_4c）

---

## 9. Windows 固有の制限

- **対応 OS**: Windows 10 / 11 のみ。macOS / Linux には非対応です（PowerShell スクリプト・パス操作が Windows 依存）。（requirements.md §1.2）
- **RotatingFileHandler のファイルロック**: Windows 環境では `RotatingFileHandler` がファイルをオープン中にローテーションが発生すると例外が起きる場合があります。シングルプロセス運用（プロトタイプの想定）では通常問題ありません。（handoff_phase6_1）

- マルチテナント対応
- DB（SQLite / PostgreSQL 等）への移行
- 過去ドラフトの履歴比較 UI

- Windows 以外の OS 対応
